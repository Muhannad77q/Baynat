# بَيّنات — سؤال اليوم

تطبيق عربي تفاعلي يساعد المشرف على:

- إنشاء حسابات مستقلة لعدة مشرفين، مع اسم ورمز دخول خاص لكل مشرف.
- إدارة قائمة طلاب مشتركة لكل المشرفين مع الاسم والصف والحلقة ورمز دخول من أربعة أرقام.
- تعديل بيانات الطالب عند الحاجة.
- إنشاء سؤال يومي من نوع اختيار متعدد، صح أو خطأ، أو إجابة قصيرة.
- مشاركة رابط السؤال مع الطلاب.
- احتساب النقاط حسب صحة الإجابة وسرعة الحل وترتيب الطالب.
- عرض لوحة المتصدرين فور إرسال الإجابة.
- متابعة سجل دائم للمشاركين والأجوبة، وإعادة تعيين نتائج سؤال اليوم دون حذف السجل.

## كيف يعمل الرابط المنفصل؟

لوحة المشرف تعمل في `/`، بينما يفتح الطالب رابطًا مستقلًا مثل:

```text
https://example.com/student.html?q=AbCd1234
```

الطالب يفتح الرابط من أي جوال، ويكتب اسمه ويختار صفّه (أولى أو ثاني أو ثالث ثانوي) وحلقته (زكاء أو سواعد)، ثم يدخل رمزه ذي الأربعة أرقام. لا يظهر نص السؤال إلا بعد نجاح الدخول وبدء مؤقت الخادم. يبقى الجواب الصحيح والرموز داخل الخادم، وتصل الإجابة إلى لوحة المشرف وتظهر في السجل والترتيب على جميع الأجهزة تلقائيًا.

عند تشغيل الخادم أول مرة، يظهر `Baynat supervisor setup key` في سجل التشغيل. أدخله مرة واحدة في لوحة المشرف، ثم اكتب اسم المشرف الأول واختر له رمزًا من ٦ خانات على الأقل. بعد الدخول، افتح صفحة «المشرفون» لإضافة حساب مستقل لكل مشرف آخر. يشاهد جميع المشرفين قائمة الطلاب والسؤال والنتائج نفسها، لكن لكل واحد اسم ورمز دخول خاص به. يمكن تحديد مفتاح تهيئة معروف مسبقًا عبر `BAYNAT_SETUP_KEY`.

## التشغيل

```bash
npm run dev
```

ثم افتح `http://localhost:5173`. ينشئ الخادم ملف البيانات الخاص به داخل `.data/`.

تبدأ النسخة الجديدة بفصل فارغ دون اسم أو طلاب تجريبيين. عند ترقية ملف بيانات قديم ذي رمز مشرف واحد، يتحول الحساب تلقائيًا إلى حساب باسم «المشرف الرئيسي»، ويمكن تعديل اسمه من صفحة المشرفين.

للتجربة من جوال آخر على الشبكة نفسها، افتح عنوان الجهاز بدل `localhost`، ثم انسخ رابط الطالب من لوحة المشرف وأرسله إلى الجوال.

## الاختبارات

```bash
npm test
```

تشمل الاختبارات حسابات المشرفين المتعددة ومساحة العمل المشتركة، والقائمة المشتركة وتعديل بيانات الطالب، ودخول أكثر من طالب من جلسات مستقلة، وسجل المشاركين والأجوبة، وإعادة تعيين النتائج، واستعادة البيانات بعد إعادة تشغيل الخادم، ومعاملات Netlify Database المتزامنة ومنع إعادة استخدام تحقق الدخول.

## النشر

### Netlify

لا يعمل التطبيق إذا نُشر مجلد `dist/` وحده أو رُفعت الملفات كنشر ثابت؛ لأن ذلك لا يجمع الدالة ولا يطبّق ترحيل قاعدة البيانات، فتفشل مسارات `/api/*`. إذا عرض Netlify Drop بناء المشروع من المصدر للحساب المسجّل، ارفع **مجلد المصدر كاملًا** وتأكد في سجل النشر من ظهور Build وFunction باسم `api` وترحيل Database. إذا نُشرت الملفات فورًا بلا سجل بناء، استخدم Netlify CLI أو اربط مستودعًا.

يتطلب النشر بناءً من المصدر: اربط المستودع بـ Netlify، أو استخدم Netlify CLI إصدار `26.0.0` أو أحدث.

لنشر المشروع من جهاز لا يستخدم Git إلى **موقع Netlify موجود**، نفّذ من جذر المشروع بالترتيب التالي، واستبدل `YOUR_EXISTING_SITE_NAME` باسم الموقع وعبارة المفتاح بقيمة سرية من ١٢ إلى ١٢٨ خانة:

```bash
npm install
npx netlify-cli@latest login
npx netlify-cli@latest link --name YOUR_EXISTING_SITE_NAME

read -rsp "BAYNAT_SETUP_KEY: " BAYNAT_SETUP_KEY && echo
npx netlify-cli@latest env:set BAYNAT_SETUP_KEY "$BAYNAT_SETUP_KEY" \
  --context production deploy-preview --scope functions --secret
unset BAYNAT_SETUP_KEY

npx netlify-cli@latest deploy --context deploy-preview
```

انسخ `Deploy URL` الذي يطبعه الأمر الأخير إلى `PREVIEW_URL`، ثم افحص سجل ذلك النشر وصحة الواجهة قبل الإنتاج:

```bash
PREVIEW_URL="https://DEPLOY_URL_SHOWN_BY_NETLIFY"
npx netlify-cli@latest logs --source deploy --url "$PREVIEW_URL" --since 10m
curl -fsS "$PREVIEW_URL/api/health"
# النتيجة المتوقعة: {"ok":true,"service":"baynat"}

npx netlify-cli@latest deploy --prod --context production
PRODUCTION_URL="https://YOUR_EXISTING_SITE_NAME.netlify.app"
npx netlify-cli@latest logs --source deploy --url "$PRODUCTION_URL" --since 10m
curl -fsS "$PRODUCTION_URL/api/health"
```

يجب أن يبيّن سجل كل نشر نجاح أمر البناء، وتجميع Function باسم `api`، وتطبيق ترحيل Database من `netlify/database/migrations/`. لا تنتقل إلى `--prod` إذا غاب أحدها أو لم تُرجع `/api/health` الاستجابة المتوقعة. ينفّذ Netlify CLI البناء المضبوط في `netlify.toml` تلقائيًا؛ يمكن تشغيل `npm run build` يدويًا للتحقق من إنشاء `dist/`، لكنه لا يغني عن نشر الدالة والترحيل.

تثبيت `@netlify/database` ثم تنفيذ نشر مبني من المصدر يجعل Netlify يوفّر قاعدة Postgres تلقائيًا في الخطط الحالية المعتمدة على الرصيد. تُحفظ حالة بَيّنات المعتمة في صف `JSON` دائم واحد، وتُحفظ تحققات الدخول المستهلكة في جدول مستقل كي لا تقفل صف الحالة. تستخدم كل كتابة مشتركة معاملة Postgres وقفل `SELECT ... FOR UPDATE` بمهل زمنية محدودة، لذلك لا تضيع التعديلات المتزامنة ولا تبقى الطلبات محجوبة حتى انتهاء ميزانية الدالة. ينشئ Netlify فرع قاعدة بيانات معزولًا تلقائيًا لكل Deploy Preview؛ لا تحتاج الدالة إلى اختيار مخزن أو قراءة سياق النشر بنفسها.

Netlify Database متاح في الخطط المعتمدة على الرصيد. إذا كان الموقع على خطة Netlify قديمة، فقد يلزم تحويله إلى خطة معتمدة على الرصيد قبل النشر. راقب استهلاك Database compute والنطاق وحدود الخطة من لوحة Netlify.

قبل أول نشر، أضف المتغير التالي من إعدادات Environment variables في Netlify واجعله متاحًا للدوال:

- `BAYNAT_SETUP_KEY`: قيمة سرية من ١٢ إلى ١٢٨ خانة. تكون مطلوبة فقط حتى إنشاء أول مشرف، وتبقى قيمة البيئة هي المعتمدة خلال هذه المرحلة. بعد نجاح إنشاء المشرف الأول تُمحى من حالة قاعدة البيانات ويمكن حذف المتغير من Netlify. لا تضع القيمة في المستودع.

ويمكن ضبط:

- `BAYNAT_ACCESS_DIFFICULTY`: من `20` إلى `24` في الإنتاج، والافتراضي `20`.
- `BAYNAT_SUPERVISOR_DIFFICULTY`: من `16` إلى `24` في الإنتاج، والافتراضي `16`.

يوفّر Netlify بيانات اعتماد Database للدالة تلقائيًا؛ لا تضف `NETLIFY_DB_URL` يدويًا ولا تشغّل ترحيلات على قاعدة الإنتاج بنفسك. يطبّق النشر الترحيلات تلقائيًا على فرع المعاينة أو الإنتاج المناسب. للتطوير المحلي استخدم `netlify dev` وطبّق الترحيلات على قاعدة التطوير المحلية فقط عبر `netlify database migrations apply`.

لا يتضمن هذا الإصدار مستورد Blobs؛ فمحول Blobs في هذا الفرع لم يصل إلى الموقع الإنتاجي. إذا نُشرت نسخة Blob يدويًا في موقع آخر، صدّر `baynat-data` وانقل بياناتها يدويًا مرة واحدة قبل تحويل الزيارات.

### خادم Node أو Docker

يمكن بدلًا من Netlify تشغيل `npm start` على استضافة تدعم عملية Node مستمرة وقرصًا دائمًا، مع ضبط `PORT` عند الحاجة. صورة Docker تحفظ البيانات في `/data`.

- شغّل عملية Node واحدة لكل ملف بيانات؛ يمنع ملف القفل تشغيل عمليتين حتى لا تضيع الإجابات. بعد توقف غير طبيعي فقط، تأكد أن كل العمليات متوقفة قبل حذف ملف `.lock` يدويًا.
- لا تضبط `TRUST_PROXY=true` إلا خلف وكيل موثوق يحذف ترويسة `X-Forwarded-For` الواردة من المستخدم ويكتبها بنفسه.
- يتحقق المتصفح تلقائيًا من كل محاولة دخول قبل فحص الاسم والصف والرمز، ولا يمكن إعادة استخدام التحقق نفسه.
- تنتهي غرف الأسئلة بعد ٣١ يومًا وتُحذف المنتهية عند إنشاء سؤال جديد.
- استخدم HTTPS في النشر الفعلي، وخذ نسخة احتياطية دورية من ملف البيانات عند استخدام خادم Node، وراجع نسخ Netlify Database الاحتياطية وحدود الاحتفاظ لخطة الموقع.
